# Self-Upgrade Agent 整体改进计划

> **For Hermes:** 使用 subagent-driven-development skill 逐任务实施。

**Goal:** 将 Self-Upgrade Agent 从"骨架可用、关键链路断裂"的状态修复为完整的自主进化闭环：多源搜索 → 精准筛选 → 代码生成 → 真实 benchmark 评估 → 统计决策 → bootloader 部署。

**Architecture:** 三阶段修复：(A) 扩展信息搜集面，(B) 建立真实评估管线，(C) 打通主链路。

**Tech Stack:** Python 3.12, httpx, selenium, langgraph, SQLite, pytest

---

## 当前状态总结

| 链路节点 | 现状 | 目标 |
|---------|------|------|
| 信息搜集 | 只有 arXiv API | arXiv + Semantic Scholar + Papers With Code + GitHub |
| 方法筛选 | keyword+LLM 三维评分可用 | +引用数信号，+动态关键词扩展 |
| 代码生成 | patchgen+sandbox+reflect 链完整 | 保持，接入主流程 |
| 效果评估 | **随机数** | 真实 benchmark 执行 + 统计显著性 |
| 决策 | 阈值逻辑正确 | （数据真实后自然生效） |
| bootloader | 只搬 upgrades/ 目录文件 | 直接读写 core/ 模块 |
| 生命周期 | skill 维度追踪 | 模块版本维度追踪 |
| 主入口 | 调用 skillgen 路径 | 调用 patchgen 路径 |

## 阶段 A：信息搜集扩展（3 个接入源 + 1 个动态策略）

### A1：Semantic Scholar API 接入

**目标：** 补上 citation_count（当前始终为 0），增加论文影响力信号，支撑筛选阶段的质量判断。

**Semantic Scholar API 要点（来自 arxiv skill / Semantic Scholar 公开文档）：**
- 免费 tier：1 req/s，无需 API key 可达到 100 req/5min
- 搜索：`GET https://api.semanticscholar.org/graph/v1/paper/search?query=...&fields=title,citationCount,year,authors`
- 按 arXiv ID 查详情：`GET https://api.semanticscholar.org/graph/v1/paper/ArXiv:{id}?fields=citationCount,influentialCitationCount,title,abstract`
- 引用链：`GET .../paper/{paperId}/citations?fields=title,citationCount` 和 `.../references`

**任务 A1.1：新建 S2 API 客户端**
- Create: `src/research_s2.py`
- 函数：`search_s2(keywords, max_results=10) → List[Paper]`
- 函数：`enrich_paper(arxiv_id: str) → dict` （取 citation_count, influential_citation_count）
- 函数：`get_citing_papers(paper_id: str, limit=5) → List[dict]`（引用链追踪）
- 函数：`get_references(paper_id: str, limit=5) → List[dict]`（被引链）
- 缓存策略：复用 `_cached_fetch` 模式（1h 缓存）
- 测试：`tests/test_research_s2.py` — mock HTTP 响应，验证解析

**任务 A1.2：将 citation 信号接入 filter 评分**
- Modify: `src/filter.py` — `ScoredPaper` 增加 `citation_score` 字段
- Modify: `src/filter.py` — `total_score` 权重调整为 `0.4×applicability + 0.25×novelty + 0.15×abstract + 0.2×citation`
- 在 `filter_papers` 中，对每篇论文调用 `enrich_paper` 获取引用量，log-scale 映射到 0-10 分
- citation_score 计算：`min(10.0, log10(citation_count + 1) * 2.5)` — 100+ 引用 → 满分
- 测试：`tests/test_filter.py` — 验证带 citation 的评分

### A2：Papers With Code 接入

**目标：** 获取 trending methods 和 benchmark 排名，发现"有可用代码且被验证过"的方法。

**PwC 数据获取方式（无官方 API，通过网页 + 非官方接口）：**
- Trending: `https://paperswithcode.com/` — 爬取首页 trending 列表
- 搜索: `https://paperswithcode.com/search?q={query}` — HTML 解析
- 每篇论文页面：`https://paperswithcode.com/paper/{slug}` — 获取 GitHub stars, benchmark 排名
- 优先级：先实现最基本的 trending 抓取，后续可扩展

**任务 A2.1：PwC trending 爬取**
- Create: `src/research_pwc.py`
- 函数：`fetch_trending_papers(max_results=10) → List[dict]`
  - 使用 httpx + BeautifulSoup（或用 selenium 回退）
  - 返回：title, arxiv_id, github_url, stars, benchmarks
- 函数：`search_pwc(query, max_results=10) → List[dict]`（搜索特定方法）
- 缓存：1h
- 测试：`tests/test_research_pwc.py` — mock HTML，验证解析

**任务 A2.2：PwC 结果融入主搜索流程**
- Modify: `src/research.py` — `search_arxiv` 改为 `search_all_sources(config)`
- 新建聚合函数，并发调用 arXiv + S2 + PwC，去重合并
- Paper 数据类增加字段：`source`, `citation_count`, `github_stars`, `benchmarks`
- 测试：验证多源去重逻辑

### A3：GitHub Trending 监控

**目标：** 发现可直接运行的代码仓库——有代码的方法比纯论文更容易集成。

**任务 A3.1：GitHub 搜索工具**
- Create: `src/research_github.py`
- 函数：`search_github_repos(query="agent framework LLM", max_results=10) → List[dict]`
  - 使用 `https://api.github.com/search/repositories?q={query}&sort=stars`
  - 需要 GitHub token（可选，无 token 速率更低）
  - 返回：name, description, stars, language, url, topics
- 函数：`search_trending_weekly(language="python") → List[dict]`
  - 爬取 `https://github.com/trending/python?since=weekly`
- 缓存：1h
- 测试：mock 响应

### A4：动态关键词扩展

**目标：** 从已发现的论文中自动提取新兴趋势关键词，不再依赖手动维护 config.yaml 的 keywords。

**任务 A4.1：关键词提取器**
- Create: `src/keyword_expander.py`
- 函数：`extract_trending_keywords(papers: List[Paper], top_n=5) → List[str]`
  - 从论文标题+摘要中提取高频 n-gram（2-4 词）
  - 使用 LLM 判断哪些 n-gram 是"新兴方法名称" vs 通用术语
  - 排除已有关键词，返回新增候补
- 函数：`merge_keywords(existing: List[str], new: List[str], max_total=15) → List[str]`
- 在每次 pipeline 运行后调用，将新关键词存入 `upgrades/trending_keywords.json`
- 测试：`tests/test_keyword_expander.py` — 验证提取和去重

## 阶段 B：建立真实评估管线

### B1：替换随机数为真实 benchmark

**当前**：`pipeline.py._run_evaluation` 用 `random.uniform(0.01, 0.10)`
**目标**：真实跑 `benchmarks/tasks.json` + 核心 agent，对比 baseline vs patched

**任务 B1.1：让 pipeline 调用真实 benchmark**
- Modify: `src/pipeline.py` — `_run_evaluation` 替换为调用 `src/benchmark.py` 的 `run_all` + `compare`
  - `dry_run=False` 时：真正运行 agent 在所有 benchmark 任务上
  - `dry_run=True` 时：保留模拟数据（用于快速验证）
- 评估流程：
  1. 记录 baseline（未打补丁的 agent 在各任务上的成功率）
  2. 临时替换 core/planner.py 为新代码（备份原文件）
  3. 记录 upgraded（打补丁后的成功率）
  4. 恢复原文件
  5. 返回 delta
- Modify: `src/pipeline_lg.py` — node_evaluate 已经做了这个，只需整合进主 pipeline

**任务 B1.2：Benchmark 任务集升级**
- Modify: `benchmarks/tasks.json` — 从 8 个通用任务扩展为 20+ 个，按能力分类：
  - `planning`: 复杂多步任务（"组织 20 人会议，列出含时间和负责人的计划"）
  - `reasoning`: 多跳推理（"A>B, B>C, C<D, D>E → 排序"）
  - `tool_use`: 需多工具组合（"读取 config.yaml 中的 evaluate.mode 值"）
  - `code_gen`: 指定格式和约束的代码生成
  - `decomposition`: 需要递归分解的问题
  - `reflection`: 自我纠错类任务（"指出以下代码中的 bug 并修复"）
- 每个任务设置 `difficulty`（easy/medium/hard）和 `category`
- 确保任务覆盖到论文中最可能改进的维度

### B2：统计显著性

**当前**：`trials_per_test: 3`，无置信区间
**目标**：每个任务跑 10+ 次，用 bootstrap 或 t-test 判断真实改进

**任务 B2.1：统计评估模块**
- Create: `src/stats.py`
- 函数：`bootstrap_test(baseline_results, upgraded_results, n_bootstrap=1000) → dict`
  - 返回：mean_delta, ci_lower, ci_upper (95%), p_value, significant (bool)
- 函数：`is_real_improvement(baseline: dict, upgraded: dict, config) → bool`
  - 检查：delta > min_delta AND ci_lower > 0 AND p_value < 0.05
- 集成到 `src/evaluate.py` 的 `compare_results`
- 测试：`tests/test_stats.py`

**任务 B2.2：提高 trial 数量**
- Modify: `config.yaml` — `evaluate.trials_per_test: 10`（默认）
- Modify: `src/evaluate.py` — 支持并行运行（thread pool），因为 LLM 调用是 IO-bound

### B3：多维度评估

**当前**：只衡量 success_rate + token_count
**目标**：增加响应质量、延迟分布、退化检测

**任务 B3.1：扩展评估维度**
- Modify: `src/evaluate.py` / `src/benchmark.py` — `BenchmarkResult` 增加：
  - `instruction_following_score`（LLM 判断是否遵循了指令中的所有约束）
  - `hallucination_flag`（检测输出中是否有与任务无关的编造内容）
  - `latency_ms`（已有 latency_seconds，改为毫秒）
- 新增函数：`compute_quality_metrics(results) → dict`
- 决策时综合多个维度（非仅 success_rate）

**任务 B3.2：退化测试**
- Modify: `src/evaluate.py` — 增加 regression test suite（5 个简单任务）
  - 这些任务必须在打补丁前后都答对
  - 如果任何一个退化 → 标记为 regression，无论主 benchmark 分数如何
- 任务集：算术计算 / 基础常识 / 简单代码执行

### B4：生命周期重评估强化

**当前**：`evaluate_all_skills` 只取前 1000 字符，跑 2 个任务
**目标**：完整的 benchmark 重跑

**任务 B4.1：重评估改为完整 benchmark**
- Modify: `src/skill_lifecycle.py` — `evaluate_all_skills`
  - 读完整 SKILL.md
  - 用完整 benchmark 任务集（20+ 任务）
  - 运行足够 trial 数
  - 启用统计显著性判断
  - 结果写入 DB，标记为"已重评估"

**目标**：promote 时直接写入 `core/planner.py`，rollback 时从备份恢复

**任务 C2.1：改造 switcher 的 promote/rollback**
- Modify: `src/switcher.py`
  - `promote_candidate(skill_name)` → 增加 `target_module` 参数（如 "planner.py"）
    - 读取 `upgrades/candidates/{skill_name}/code.py`
    - 备份 `core/{target_module}` → `upgrades/backups/{target_module}_{timestamp}.bak`
    - 写入新代码到 `core/{target_module}`
    - 更新 manifest
  - `rollback_active(skill_name)` → 从最新备份恢复 `core/{target_module}`
  - `get_active_skills()` → 返回当前 core 模块版本信息，而非 upgrades/active 目录
- 目录结构改为：
  ```
  upgrades/
  ├── candidates/{skill_name}/code.py   # 候选代码
  ├── backups/{module}_{timestamp}.bak  # 核心模块备份
  ├── history.db                        # 版本历史
  └── manifest.json                     # 当前活跃版本清单
  ```

**任务 C2.2：增加原子写入和版本号**
- `core/` 下每个模块文件增加 `__version__` 变量
- promote 时更新版本号

### C3：调度器健壮化

**任务 C3.1：改进 daemon 模式**
- Modify: `run.py` — `--daemon` 选项

  - 异常重启逻辑：失败后等待 5 分钟重试，最多 3 次后跳过本轮
  - 日志轮转：`upgrades/daemon.log` 文件，超过 10MB 轮转
  - 优雅关闭：SIGINT/SIGTERM 处理
- 增加 `--schedule` 输出的 crontab 格式精确到每 6 小时（不仅是每日），因为 arXiv 每天更新

## 实施顺序

```
阶段 A（信息搜集）：A1 → A2 → A3 → A4
    ↓（约 3-4h）
阶段 B（真实评估）：B1 → B2 → B3 → B4
    ↓（约 3-4h）
阶段 C（打通链路）：C1 → C2 → C3
    ↓（约 2-3h）
阶段 D（收尾）：D1 → D2 → D3
    ↓（约 1-2h）
───────────────────
总计：约 9-13 小时
```

每个阶段的最后一个任务是该阶段的集成测试：确保所有新增代码的测试通过，且不影响已有功能。
